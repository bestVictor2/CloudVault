## 2. 面试可能出的题目（高频 + 深挖）

### 系统设计题（综合）
1. 设计一个支持 10GB 以上文件上传、断点续传与秒传的系统，需要哪些核心表、关键流程？
答：
核心表包括：
- `file_object`（hash、bucket、object_name、size、ref_count）
- `user_file`（目录树与权限）
- `upload_session`（file_hash、file_size、chunk_size、total_chunks、状态）
- `file_chunk`（upload_id、chunk_index、etag/size）
- 必要时 `share_link`
关键流程：
初始化会话
→ 分片上传（幂等写入 chunk 记录）
→ 合并（分布式锁，防重复合并）
→ 计算/校验 hash
→ 秒传复用（已存在对象则仅创建 user_file 并加 ref_count）
→ 失败补偿与回滚（清理会话/未完成分片）。
还要考虑上传续传的查询接口、合并后的对象写入与元数据事务一致性。
2. 如何设计对象存储与业务元数据解耦？有哪些一致性问题？
答：
对象存储只负责大对象读写，
业务语义与权限放在数据库中，
通过 `file_object` 与 `user_file` 关联。
数据面与控制面拆分可以降低存储耦合。
一致性问题常见有：
- 对象写入成功但 DB 事务失败，产生“孤儿对象”
- DB 成功但对象写入失败，产生“空引用”
- 删除时 ref_count 竞争导致误删
- 跨服务并发合并导致重复对象
解决方式：
写入时先对象后 DB 并做补偿清理，
或使用事务外补偿任务；
删除使用幂等与延迟回收；
合并使用分布式锁与幂等检查；
周期性巡检修复（对象存在性与 DB 引用一致性）。
3. 设计离线下载任务系统，如何处理重试、失败、限速与任务可观测？
答：
采用 MQ（如 RabbitMQ）作为任务队列，
任务表或 Redis 记录状态（PENDING/RUNNING/SUCCEEDED/FAILED）。
重试采用指数退避和最大重试次数，
失败后入 DLQ 供人工或自动修复。
限速在 Consumer 侧实现（令牌桶/并发上限/按用户限速）。
可观测包括任务生命周期日志、失败原因字段、
以及指标（处理时长、成功率、重试次数、队列堆积）。
需要确保任务幂等（按 task_id 去重）
和断点恢复（保存中间文件或偏移）。
4. 如何在高并发场景下做文件去重？如何处理 hash 冲突与对象丢失？
答：
高并发下通过 hash 索引 + 唯一约束 + 分布式锁，
确保同一 hash 只写一次对象。
流程通常是先查缓存/DB，
未命中时抢占锁再写对象并建元数据。
hash 冲突通过强 hash（SHA-256），
并在合并后做 size + hash 二次校验，
极端场景可引入双 hash。
对象丢失需要定期巡检与修复流程
（比对对象存储与 DB 引用），
对缺失对象可触发重新上传
或标记为不可用并通知用户。
5. 设计一个大规模文件分享系统，如何处理分享链路、安全与权限？
答：
核心表包含 share_link
（token、owner_id、object_id、权限、过期时间、访问次数限制）
与访问日志。
链路上使用短期可撤销 token，
配合预签名 URL 或服务端代理下载。
权限控制需校验分享者是否有权限
与分享范围（只读/可下载/可转存）。
安全措施包括限流、防刷、token 失效与黑名单、
以及敏感文件的二次校验。
扩展上可做分享水印、访问审计与按区域/CDN 分发。

### 大文件上传细节题
1. 为什么要使用上传会话？upload_id 需要包含哪些字段？
答：
上传会话用来跟踪大文件的分片状态，
支持断点续传和并发控制。
upload_id 通常关联：
`file_hash`、`file_size`、`chunk_size`、`total_chunks`、
`user_id`、`bucket`、状态与过期时间。
这样可以校验分片合法性、支持续传查询，
并在合并时校验文件完整性。
2. 分片上传如何做到幂等？
答：
以 `(upload_id, chunk_index)` 作为唯一键，
重复上传同一分片时返回已存在结果或覆盖一致数据。
存储层可校验 etag/size，避免重复写入。
分片状态写入 DB 或 Redis 时使用幂等更新，
确保并发请求不产生重复记录。
3. 合并阶段如何避免重复合并？
答：
使用分布式锁或 DB 状态机，
例如将 upload_session 从 UPLOADING 原子切换到 MERGING，
确保只有一个合并执行。
合并完成后写入 `file_object` 并标记会话完成。
若重复请求到达，
直接返回已完成结果或从元数据读取对象信息。
4. 为什么 hash 在后端算？如果客户端算会有什么风险？
答：
客户端 hash 可被伪造，
可能导致秒传绕过、错误复用或覆盖他人文件。
后端计算保证真实性，
能结合存储实际内容做一致性校验。
客户端可先传弱 hash 用于快速检查，
但最终应由服务端做强 hash 校验。
5. 上传的分片如果重复上传/错序上传怎么办？
答：
重复上传通过幂等键处理，直接返回成功。
错序上传只要以 chunk_index 标记即可，
合并时按序拼接。
若分片损坏或大小不一致，
应拒绝该分片并要求重传，
同时记录错误码便于客户端恢复。

### 秒传/去重题
1. file_object 与 user_file 的关系如何设计？为什么要分表？
答：
`file_object` 表存储物理对象信息
（hash、size、存储位置、ref_count），
`user_file` 表存储用户目录与文件引用
（name、parent_id、object_id）。
分表实现业务视角与物理存储解耦，
便于共享与去重，
避免在对象层混入权限、目录等业务语义。
2. 引用计数在哪些场景会出错？如何修正？
答：
并发创建/删除、事务失败或重复请求
都会导致 ref_count 错误。
修正方式包括：
使用事务或分布式锁保证增减原子性；
对 ref_count 做下限校验；
周期性全量校验（统计 user_file 引用数并回写）；
对异常值触发人工或自动修复。
3. 删除时如果对象仍被引用，如何安全处理？
答：
删除 `user_file` 时先减 ref_count，
只有 ref_count 归零才触发对象删除。
实际删除可延迟执行，避免竞态。
可将“待删除对象”进入回收队列，
确保最终一致性与误删可恢复。
4. 如果对象存储丢对象了，如何恢复？
答：
通过巡检发现对象缺失后，
将 `file_object` 标记为缺失并阻止新引用。
若存在其他来源（例如多副本、冷备、用户本地重传）
可触发修复。
没有备份时需返回错误并提示用户重新上传，
避免出现隐性数据损坏。

### MQ 与异步任务题
1. 什么情况下需要离线下载队列？
答：
当下载耗时长、需要合并/打包、
依赖外部源或需要控制并发与带宽时，
应使用离线队列。
它可避免同步接口超时，
并支持任务排队、恢复与审计。
2. 如何做失败重试与延迟重试？
答：
失败重试采用指数退避并记录重试次数，
避免依赖被打爆。
延迟重试可使用延迟队列或死信交换机回流。
重试应保证幂等并记录最后失败原因。
3. 为什么需要 DLQ？DLQ 里的任务如何处理？
答：
DLQ 用于隔离长期失败或异常任务，
防止阻塞主队列。
DLQ 任务应由人工或自动修复流程处理，
例如重新配置下载源、修复权限后再投递，
或标记为永久失败并通知用户。
4. 任务并发控制在 Producer 侧还是 Consumer 侧？
答：
主要在 Consumer 侧控制更可靠，
因为实际执行发生在消费端。
可按 worker 数、队列 prefetch、令牌桶实现。
Producer 可做粗粒度限流，
但不应依赖它来保证系统稳定性。
5. Redis/DB 如何做任务状态查询？
答：
DB 存持久状态（任务表），
Redis 存热点状态与进度缓存。
查询时先读 Redis 未命中再读 DB。
更新时采用“写 DB + 失效 Redis”
或“写 DB 同步写 Redis”的策略，
确保用户看到最新状态。

### Redis 与一致性题
1. 缓存哪些数据最合适？
答：
高频读、变更频率低且计算成本高的数据，
如 `file_object`、用户文件列表、上传会话状态、
分享链接元数据。
对强一致要求高或频繁写的数据应谨慎缓存
或缩短 TTL。
2. 失效策略是删缓存还是过期？
答：
对一致性要求高的数据，
优先“写 DB 后删缓存”。
对允许短暂不一致的数据可用 TTL 过期。
可结合双删策略（写后删 + 延迟再删）
减少并发读到旧值的概率。
3. 分布式锁可能导致的问题（死锁、锁误删）如何处理？
答：
设置合理过期时间避免死锁。
使用唯一 token 标识锁持有者，
释放时校验 token 防误删。
延长任务时使用续租机制。
必要时引入 Redlock 或基于 DB 的乐观锁方案。

### 下载与带宽题
1. 直链下载的优势与风险？
答：
优势是服务端负载低，
带宽成本可转移到对象存储或 CDN。
风险是直链泄露导致滥用与越权，
需要短期预签名、访问控制与限速。
对私有文件应限制有效期与下载次数。
2. ZIP 打包下载大文件时如何避免内存爆？
答：
采用流式打包与边读边写，
不将文件全部加载到内存。
使用临时文件或分块流输出。
必要时限制单任务总大小与并发数，
避免 IO 与带宽被耗尽。
3. 流式下载如何保证断点续传？
答：
支持 Range 请求并在对象存储层或代理层
正确处理字节范围。
记录已下载偏移并在重试时从 offset 继续。
需要校验内容长度与 ETag，
防止断点续传到错误版本。

### 安全与权限题
1. 分享链接如何防止滥用？
答：
使用随机高熵 token、短期有效期、
次数或 IP 限制，配合访问日志与告警。
支持分享者随时撤销。
对敏感分享可要求二次验证或验证码。
2. 预签名 URL 的有效期、权限控制如何做？
答：
有效期尽量短（分钟级），
权限只授予下载或上传的最小权限。
绑定对象路径与方法，
必要时限制来源 IP 或用户身份。
过期或撤销后应拒绝访问并重新获取新签名。
3. 上传过程中如何防止越权/篡改/Hash 欺骗？
答：
上传接口验证用户权限与目标路径。
分片上传需校验 upload_id 与 user_id 绑定关系。
服务端计算 hash 与 size 校验防伪造。
对关键字段使用签名或 nonce 防篡改与重放。

## 3. 核心技术设计思路（面试官视角）

### 3.1 对象存储 + 元数据解耦
**设计目标**
- 对象存储只负责大文件读写，
  不承载业务语义
- 业务层通过 DB 维护
  “文件对象”与“用户文件”关系

**关键实体**
- `file_object`：存储真实对象
  （hash、bucket、object_name、size、ref_count）
- `user_file`：用户视角的目录树结构
  （name、parent_id、object_id）

**为什么这样设计**
- 同一个对象可被多个用户/分享引用
- 数据结构清晰，
  便于权限控制与回收策略

**迭代路径**
1. V1：简单表结构，
   仅支持上传/下载
2. V2：加入 hash 去重与 ref_count
3. V3：加缓存与分布式锁，
   解决高并发一致性

**扩展方向**
- 多桶策略（冷热分层）
- 对象版本管理（历史版本）

---

### 3.2 分片上传 + 断点续传
**设计目标**
- 支持大文件上传
- 允许断点续传
- 合并阶段幂等安全

**关键流程**
1. `MultipartInit` 创建上传会话
2. `UploadChunk` 上传分片并记录状态
3. `MultipartComplete` 合并分片 → 生成对象

**关键设计点**
- upload_session 保存
  file_hash、file_size、chunk_size、total_chunks
- file_chunk 记录 upload_id + chunk_index
- 分布式锁保证合并阶段幂等

**迭代路径**
1. V1：单请求上传（不可续传）
2. V2：加入 upload_session + chunk
3. V3：加入 hash 校验与分布式锁

**扩展方向**
- 并发分片上传（控制 max concurrency）
- 合并时流式拼接而非 Copy

---

### 3.3 秒传 + 去重存储
**设计目标**
- 相同文件只存一份
- 秒传提升用户体验

**关键流程**
1. 客户端提交 hash
2. 服务端校验 hash 对象是否存在
3. 存在则创建 user_file 绑定

**关键设计点**
- hash 应由服务端计算（防伪造）
- ref_count 用于对象生命周期

**扩展方向**
- 弱 hash + 强 hash 双重校验
- 透明压缩/去重

---

### 3.4 离线下载任务系统
**设计目标**
- 大文件下载不阻塞用户请求
- 支持任务查询与恢复

**关键流程**
1. 任务入队（RabbitMQ）
2. Worker 消费与执行
3. 状态存储（DB/Redis）
4. 失败重试 & DLQ

**关键设计点**
- 并发控制、限速策略
- 延迟重试（避免打爆依赖）

**扩展方向**
- 多种下载源（HTTP/FTP）
- 多级队列与优先级

---

### 3.5 Redis 缓存与一致性
**设计目标**
- 高并发读提升性能
- 保证关键数据一致性

**关键点**
- 缓存 file_object、user_file 列表
- 删除或更新时主动失效
- 分布式锁避免重复合并

**扩展方向**
- 读写分离缓存
- 缓存预热与热点降级

## 4. 设计迭代过程（建议面试表述模板）

你可以这样回答设计迭代过程：

1. **初期阶段**：
   只做基础上传下载，数据存对象存储
2. **体验优化**：
   引入分片上传和断点续传
3. **效率优化**：
   引入 hash 去重与秒传
4. **高并发保障**：
   Redis 分布式锁 + 缓存
5. **异步任务体系**：
   RabbitMQ 做离线下载、异步处理

这样讲既清晰又符合工程实际。

## 5. 面试官常问追问与建议答法

### Q1: hash 冲突怎么办？
答：
采用 SHA-256 基本可忽略冲突，
但仍可在合并后做二次校验（size + hash）。
若业务要求严格，可引入双 hash。

### Q2: 合并阶段为什么要用分布式锁？
答：
防止并发触发多次合并，
避免对象重复写入和脏数据。

### Q3: 为什么后端计算 hash？
答：
客户端可伪造 hash，
会破坏秒传一致性与安全性。
